# 設計上の論点(議論用)

README の構想をもとに、実装前に決めるべきことを洗い出した。
各論点は「問い / 選択肢 / 推奨 / 理由」の形にしてある。推奨はあくまで叩き台。
決まったものは末尾の「決定ログ」に移す。

---

## 0. 現時点で決まっていること(READMEから読み取れる前提)

- 対象は学生・研究者。1人で使う前提に読める。
- コアループ: キーワード → 読むべき論文リスト → スケジュール → 「今日の論文」 → 自分でメモ → その後に AI 要約・メモ採点 → カレンダーに記録。
- 設計原則: **AI要約はメモを書く前には見せない**(自分で読ませて血肉にする)。
- LLM は「自前の API キー」または「ローカルにあるもの(Ollama 等)」を使う。
- 論文リストは LLM 生成に加えて手入力も可。
- 色は青と白の2色(死刑機能はこの制約外でも可)。
- 死刑機能はゲーミフィケーション。オフにできる。UI は本体と分離して設計する。
- LLM の担当: 論文リスト生成、要約、メモ採点、命乞いワード生成。

## 1. 形態・基盤

### Q1. アプリの形態は何か
- 問い: Web アプリ / デスクトップアプリ / モバイル / CLI のどれか。
- 選択肢:
  - (a) ブラウザで動くローカル Web アプリ(サーバー不要、データはブラウザ内)
  - (b) デスクトップアプリ(Tauri / Electron)。ローカルファイルと OS 通知が素直に使える
  - (c) サーバーありの Web サービス(アカウント制)
  - (d) モバイルアプリ
- 推奨: (b)、または (a) を PWA にして後で (b) に包む。
- 理由: 「API キーはローカルに置く」「通知を出す」「PDF やメモをファイルとして持ちたい」を全部満たすのはデスクトップが最も楽。サーバーありにすると API キーの預かりと課金の問題が出る。
- **決定: (b)。理想は (d) モバイルなので、将来モバイルに持っていける構成を選ぶ(Q4 参照)。**

### Q2. ユーザーは1人か、複数か
- 問い: ログイン・アカウントは必要か。
- 推奨: 最初は1人用・アカウントなし。
- 理由: 課題(多読のモチベ)は個人の習慣化の話で、共有機能は構想に出てこない。マルチユーザーは後から足せるが、最初から入れるとコストが数倍になる。

### Q3. データはどこにどう保存するか
- 問い: メモ・論文リスト・カレンダー・使用量ログの保存先と形式。
- 選択肢:
  - (a) フォルダに Markdown + JSON(Obsidian 的。他ツールで開ける)
  - (b) SQLite 1 ファイル
  - (c) ブラウザの IndexedDB
- 推奨: (a) メモは `.md`、論文リストと状態は JSON または SQLite の併用。
- 理由: 「メモが自分の血肉」という思想なら、アプリを捨ててもメモが残るファイル形式が合う。検索や集計は SQLite が楽なので、インデックスとして持つ。

### Q4. 技術スタック
- 問い: 言語・フレームワーク。
- 推奨: Tauri 2 + React/TypeScript。
- 理由: Q1 で「デスクトップだが将来モバイル」と決まった。Tauri 2 は同じコードベースから iOS/Android にも出せるので、(d) への道を残せる。Electron はモバイルに出せない。
- 補足: Tauri のバックエンドは Rust。ロジックの大半(LLM 呼び出し、学術 API、SQLite)は Rust 側か TypeScript 側かを決める必要がある。モバイル移植を見据えるなら **UI は TypeScript、ファイル・通知・DB など OS 依存部分だけ Rust** に寄せるのが無難。
- **決定待ち: Rust 側にどこまで置くか。**

## 2. 論文の取得(レコメンド)

### Q5. 「読むべき論文リスト」をどうやって作るか
- 問い: README では「LLM の deep research 的な検索」とあるが、これは API として安定して存在するものではない。
- 選択肢:
  - (a) LLM に直接「キーワードに関する論文を列挙せよ」と頼む(存在しない論文を捏造するリスクが高い)
  - (b) 学術 API(Semantic Scholar / OpenAlex / arXiv / Crossref)で検索し、LLM は「検索クエリ生成」「候補の順位付け」「読むべき理由の生成」だけを担当する
  - (c) Web 検索ツール付きの LLM(各社の検索機能)に投げる
- 推奨: (b)。
- 理由: 書誌情報・DOI・PDF リンクは API から取れば正確。LLM は判断と説明に専念させると捏造を防げる。(c) はプロバイダ依存が強く「ローカル LLM でも動く」と両立しない。

### Q6. PDF はどこまで扱うか
- 問い: PDF の取得・保存・表示をアプリがやるか、リンクを開くだけか。
- 選択肢:
  - (a) リンクを外部ブラウザで開くだけ
  - (b) オープンアクセスのものは自動ダウンロードしてローカル保存
  - (c) アプリ内に PDF ビューアを持つ
- 推奨: 最初は (a)+(b)。ビューアは後回し。
- 理由: 有料誌は取れないので「取れたら保存、取れなければリンク」で割り切る。AI 要約に本文が要るなら (b) は必要。

### Q7. 論文リストのスキーマ
- 問い: CSV/JSON の列を確定させたい。
- 叩き台:
  | 列 | 必須 | 備考 |
  |---|---|---|
  | id | ○ | DOI があれば DOI、なければ生成 |
  | title, authors, year | ○ | |
  | venue | | 誌名・会議名 |
  | doi, url, pdf_url | | |
  | abstract | | API から取れる範囲 |
  | reason | | 「読むべき理由」(LLM 生成) |
  | source | ○ | llm / manual / import |
  | status | ○ | unread / scheduled / read / skipped |
  | scheduled_date, read_date | | |
  | bibtex | | 書誌情報のエクスポート用 |
- 論点: インポート形式は CSV だけでよいか、BibTeX や DOI の羅列も受けるか。
- 推奨: CSV と DOI 羅列を最初にサポート。BibTeX は後。
- **決定: 推奨通り。BibTeX はいずれ使うので、スキーマに `bibtex` 列を残し、インポート/エクスポートは v1 以降で対応。**

## 3. スケジュールと「読了」

### Q8. 「今日の論文」はどう決まるか
- 問い: リストのどれを今日に割り当てるか。
- 選択肢: リスト順 / ユーザーが並べ替えた優先順 / ランダム / LLM が難易度や関連で並べる
- 推奨: ユーザーが並べ替えられるキュー。デフォルトはリスト順。
- 理由: 自動で賢くするより、自分で決めた順で読む方が納得感がある。
- **決定: キューはユーザーが並べ替え可能。「今日の論文」画面にスキップボタンを置く。LLM による並べ替え(難易度順・関連順など)も機能として持つ。**

### Q9. 読まなかった日の論文はどうなるか
- 問い: 翌日に持ち越すか、飛ばすか。「今日の論文を差し替える」は許すか。
- 推奨: 持ち越し。差し替え(スキップ)は可能だが死刑機能側で「猶予を消費」扱い。
- 理由: 飛ばせると「読みたくない論文」が溜まって形骸化する。ただしどうしても読めない論文はあるので出口は残す。
- **一部決定: スキップは可能(Q8)。ただし Q18 で「デフォルトは猶予なし」と決まったので、スキップは猶予を消費しない。**
- **残る論点: スキップした論文はどこへ行くか。(a) キューの末尾に戻す (b) `skipped` にして二度と出さない (c) ユーザーに選ばせる。推奨は (a) で、リストから明示的に削除すれば (b)。**

### Q10. 「1日」の境界と休み
- 問い: 日付の切り替わりは 0 時か、深夜作業を考慮して 4 時などか。土日設定・長期休暇の扱い。
- 推奨: 切り替え時刻を設定可能(デフォルト 4 時)。休みは曜日指定 + 期間指定の両方。
- 理由: 深夜に読んで 0 時を跨いで死ぬのは理不尽。

### Q11. 「読んだ」の完了条件は何か
- 問い: 何をもって「1本読んだ」と判定するか。これが死刑判定の根拠になるので重要。
- 選択肢:
  - (a) メモを保存した
  - (b) メモが一定文字数以上
  - (c) メモの各テンプレート項目が埋まっている
  - (d) 「読了」ボタンを押す(自己申告)
- 推奨: (a) かつ最低文字数(例: 200 字)。テンプレートは推奨だが必須にしない。
- 理由: 厳しすぎると続かない、緩すぎると死刑が機能しない。文字数は設定可能にする。

### Q12. 1日に複数本読める場合の扱い
- 問い: 貯金(先読み)は認めるか。
- 推奨: 認めない、または「猶予日を1日獲得」に変換する上限付き。
- 理由: 貯金を認めると「週末にまとめて」になり、毎日読む習慣化の目的から外れる。
- **決定: 2 本目以降を読んだら「毎日の習慣にすべき」という警告を出したうえで猶予日を 1 日獲得。設定で変更可能。**
- **要確認: Q18 で「デフォルトは猶予の概念なし」と決まった。両立させるなら「デフォルト設定では 2 本目以降は記録に残るだけで何も得ない。設定で猶予を有効にすると、2 本目以降が猶予日に変換される」となる。この解釈でよいか。**

## 4. メモと AI

### Q13. メモのテンプレート
- 問い: 自由記述か、構造化するか。構造化するなら項目は何か。
- 叩き台(Markdown の見出し):
  1. 何を解いた / 論じた問題か(1行)
  2. 手法の要点
  3. 結果・主張
  4. 自分の言葉で言うと / 自分の研究との関係
  5. 疑問・批判
- 推奨: このテンプレートを初期値として置き、消してもよい。
- 理由: 採点(Q15)の基準を作るには、何を書くべきかの合意が先に要る。
- **決定: 叩き台通り。項目 1 は「解いた / 論じた」に修正(理論・サーベイ系の論文にも合うように)。**

### Q14. AI 要約の入力は何か
- 問い: LLM に論文の何を渡すか。
- 選択肢:
  - (a) アブストラクトのみ(常に可能、安い)
  - (b) PDF 全文(取れた場合のみ。1本あたり 1〜3万トークン)
  - (c) ユーザーが貼り付けたテキスト
- 推奨: (b) が取れれば (b)、無理なら (a)。(c) は手動オプション。
- 理由: 全文がある方が要約と採点の質は上がるが、有料誌は取れないので fallback が要る。
- **決定: デフォルトは (a) アブストラクトのみ。全文 (b) は論文ごとにユーザーが選ぶ。選ぶ前に推定コスト(トークン数と概算金額)を提示し、それでも望む場合のみ実行。**
- 実装上の含意: 全文のトークン数を事前に数える必要がある。PDF からテキスト抽出 → トークン数概算 → 確認ダイアログ、の順。Q17 の単価表がここでも使われる。

### Q15. メモ採点の基準と出力形式
- 問い: 何を点数にするか、何点満点か、点数だけかコメントもか。
- 叩き台のルーブリック:
  - 問題設定を把握しているか
  - 手法を自分の言葉で説明できているか
  - 結果を正しく捉えているか
  - 自分の視点(疑問・応用)があるか
- 推奨: 各項目 5 段階 + 短い改善コメント。合計点をカレンダーに表示。
- 理由: 点数だけだと学びがなく、コメントだけだと記録に残しにくい。
- 補足論点: 採点は「メモに書いたこと」だけを見るのか、「論文にあってメモにないこと」も指摘するのか。後者は本文が要る。

### Q16. LLM プロバイダと抽象化
- 問い: 最初にどれを対応するか。Anthropic / OpenAI / Ollama(ローカル)。
- 推奨: プロバイダを差し替えられる薄い層を最初から作り、初期対応は API 1 社 + Ollama。
- 理由: README の「API キーかローカル」を両立させるには最初から抽象化しておかないと後で苦しい。
- 補足論点: プロンプトと出力の言語は日本語で固定するか、設定にするか。

### Q17. API 使用量の表示
- 問い: 「なんぼ使ったか」をどう出すか。
- 推奨: 呼び出しごとにトークン数を記録し、プロバイダ別の単価表から概算金額を出す。月次・累計。
- 理由: 正確な請求額は API から取れないことが多いので概算にする。単価表は手で更新できる形に。

## 5. 死刑機能(2026-09-15 に取り下げ。以下は経緯として残す)

### Q18. 状態遷移をどう定義するか
- 問い: 生存 → 死亡の間に何があるか。死んだらどうなるか。
- 叩き台:
  - `alive` → (読まない日) → `warning`(猶予がある場合) → (猶予切れ) → `dead`
  - `dead` から復帰する条件: 翌日読めば新しい囚人として復活(連続記録はリセット)
- 論点:
  - 猶予は「月に n 日」か「連続で n 日」か、それとも貯めるものか
  - 死亡時に失うものは連続記録だけか、蓄積した「肉」もか
  - 墓は残るか(墓地画面 = 過去の失敗の記録)
- 推奨: 猶予は月 2 日付与・繰越なし。死亡で連続記録リセット、肉は半減、墓は墓地に残る。
- 理由: 失うものがないと緊張感がなく、全部失うと再開する気が失せる。
- **決定: デフォルトは猶予なし(読まなかった日 = 即死)。猶予は設定で有効化するオプション扱い。**
- **残る論点: 死亡時に失うもの(連続記録のみ / 肉も)と、墓を残すか。推奨は「連続記録リセット・肉は半減・墓は墓地に残る」のまま。**

### Q19. アバターと「肉」の表現
- 問い: アバターはどう作るか、肉はどう増えるか。
- 選択肢: 写真アップロード / 用意したパーツを選ぶ / 画像生成
- 推奨: パーツ選択(ピクセルアート程度)。肉はメモ文字数か採点結果に応じて段階的に増える。
- 理由: 写真は加工が難しく、画像生成は毎回コストがかかる。

### Q20. 通知
- 問い: いつ、どの経路で通知するか。
- 叩き台: 朝「今日の論文はこれ」、夕方〜夜「まだ読んでない」、締切 1 時間前に命乞い。
- 経路: OS 通知(デスクトップ)/ブラウザ通知。メール・Slack は後回し。
- 論点: 命乞いワードは通知ごとに LLM 生成するか、日 1 回まとめて生成してキャッシュするか(コストと待ち時間)。
- 推奨: 日 1 回生成してキャッシュ。ローカル LLM なら都度でも可。
- **決定: まずは OS 通知。Slack / LINE への配信はいずれ対応したい。モバイル化 (Q1 の (d)) の動機も通知にある。**
- 実装上の含意: デスクトップアプリはウィンドウを閉じると通知を出せない。「アプリを閉じても通知が来る」を実現するには (a) 常駐(メニューバー/トレイ)にする、(b) OS のスケジューラに小さなジョブを登録する、(c) Slack/LINE 配信を外部(クラウド関数など)から行う、のいずれかが要る。(a) が最も簡単で、Tauri は対応している。Slack/LINE 配信も常駐プロセスから Webhook を叩けば実現できる。**この「常駐にするか」を Q20 の追加論点とする。**

### Q21. オフにしたとき何が残るか
- 問い: 死刑機能オフ時に、連続記録・猶予・通知はどうなるか。
- 推奨: 連続記録と読了ログは本体側に持ち、死刑機能はそれを「読む」だけの表示層にする。オフにしても記録は続く。
- 理由: README の「UI を分けて設計する」を実現するには、データも分離しておく必要がある。
- **決定: 推奨通り。死刑機能オフの状態を「シンプル機能」と呼ぶ。連続記録の表示はシンプル機能でも出す。**

## 6. スコープと優先順位

### Q22. MVP に何を入れるか
- 叩き台:
  - **MVP(まず動かす)**: 論文リスト(手入力 + CSV)、今日の論文、メモエディタ、読了判定、カレンダー、AI 要約 + 採点(1 プロバイダ)
  - **v1**: 学術 API 連携によるレコメンド、使用量表示、死刑機能(状態遷移 + アバター + 通知)
  - **v2**: 命乞いワード、論文の読み方講座、ポモドーロ、BibTeX、PDF ビューア
- 論点: 死刑機能はこのアプリの「顔」なので MVP に入れるべきという考え方もある。
- 推奨: MVP には「連続記録の表示」だけ入れ、アバターと通知は v1。
- 理由: コアループが動かないと死刑機能の判定根拠がない。ただし連続記録だけは安いので最初から。
- **質問(ユーザー): あとからスコープを変えたらどんな問題があるか。UI は対話しながら細かく変えたい。**
- **回答: スコープは「作る順番」であって「設計の固定」ではないので、あとから変えること自体は問題ない。ただし、あとから変えると高くつくものと安いものがある。**
  - 安い(いつでも変えてよい): 画面のレイアウト、色、文言、ボタン配置、画面遷移。UI は対話しながら変える前提で作る。
  - 高い(最初に決めておきたい):
    1. データの形式。メモの `.md` の構造、論文リストのスキーマ(Q7)、読了ログの形。あとから変えると過去データの移行が要る。
    2. 本体と死刑機能の境界(Q21)。本体が「読了ログと連続記録」を持ち、死刑機能はそれを読むだけ、という境界を最初から守る。
    3. LLM プロバイダの抽象化(Q16)。最初に 1 社べた書きすると後で全呼び出しを書き直す。
    4. 読了の定義(Q11)。これを変えると過去の連続記録の意味が変わる。
- **決定: MVP は「作る順番」として扱い、UI は自由に変える。上記 4 点だけは先に決めて守る。**

### Q23. 講座とポモドーロ
- 問い: 論文の読み方講座は静的な文章か、LLM 対話か。ポモドーロはメモエディタと連動するか。
- 推奨: どちらも v2。講座は静的な Markdown を数本置く程度から。
- 理由: 本筋(読ませる・記録させる)に直接効かない。
- **決定: 講座は静的な文章。ポモドーロは優先度低。「作ってみて要るか判断する」扱いで v2 に置く。**

## 8. ターゲットの絞り込み(2026-09-17)

### Q24. 誰のためのアプリか
- 問題: 「学生・研究者」では広く、機能が誰向けかあやふやになる。BibTeX・検索ソース選択・Ollama・使用量表示は
  「すでに読む習慣があって効率化したい研究者」向けで、この層には Zotero / Paperpile / alphaXiv などがある。
- **決定: 研究室に配属されたばかりの B4〜M1 で、読まなきゃと思いながらショート動画を見てしまう人。** 作者自身がこの人。
  - 輪講や卒論という外圧がある / 分野の地図を持っていない / 読む習慣がまだない、の 3 つが揃う。
- この人に対する今の設計のズレ:
  1. 入口が重い(API キーの取得、5 見出しのテンプレート、200 字)。記録が面倒なのではなく、始められない。
  2. 敵はスマホにいるのに主戦場がデスクトップ。
  3. 何を読むべきか分からない。キーワード検索は地図を持っている人向け。
- 変えないもの: 「先に自分で書き、そのあとに AI 要約を見る」順序。これがこのアプリの核。

### Q25. 読了を段階にする(Q11 の改訂)
- 案: Lv1 ひとこと(既定 20 字)/ Lv2 要点(既定 80 字)/ Lv3 しっかり(`min_memo_chars`、既定 200 字)。
  Lv1 で読了が成立し、連続記録が続く。あとから書き足せば段階は上がる。下がらない。
- Q22 で「読了の定義を変えると過去の連続記録の意味が変わる」とした点: `completed` の意味は「Lv1 以上」に広がるが、
  過去の読了はすべて 200 字以上なので Lv3 として読む。過去の記録は 1 日も変わらない。
- テンプレートの先頭に「ひとこと」の見出しを足す。5 見出しを前にして手が止まるのを避ける。
- **決定: 採用。** 理由: 始めるハードルを極端に下げ、始めたら続きも読んでしまう流れを狙う。

### Q26. 読了を研究室の Slack に投稿する
- 取り下げた死刑機能(Q18-Q21)の代わり。罰ではなく、人に見られていることを動機にする。ラボにも価値がある。
- 通知の Webhook とは別の URL にする。理由: 「まだ読んでいません」が研究室のチャンネルに流れるのを避ける。
- 投稿するのは、タイトル・書誌・リンク・連続記録・メモの最初の 1 行。メモ全体は出さない。
- **決定: 採用。読了が成立したとき自動で投稿(設定で有効にした人だけ)。失敗したら手で送り直せる。**

### Q27. LLM の費用を誰が持つか(2026-09-18)
- 問題: このターゲットは API キーを取らない。一方で、AI の要約の質は API のモデルが一番よい。
- **決定: どれか 1 つに決めず、ユーザーが LLM を使う道を広く残す。**
  1. API: Anthropic / Ollama に加えて **OpenAI 互換**(OpenAI、無料枠のある Gemini、OpenRouter、LM Studio など)。
  2. **Apple Intelligence(ショートカット経由)**: ショートカット App の「モデルを使用」は、オンデバイスのほか Private Cloud Compute も選べて、無料・キー不要。
     ブラウザ版から URL で起動し、終わったら戻ってくる。Xcode もネイティブアプリも要らない。作者の手元で Apple Intelligence が動くのは M 系の iPad だけ(Mac は Intel)。
  3. **好きな AI に貼り付ける**: プロンプトをコピーして ChatGPT などに貼り、回答を貼り戻す。どの端末でも動く最後の砦。
  4. AI なし: 読む・書く・記録・Slack 共有だけで習慣は成立する。
- キーが無いときは自動で 2 か 3 になる。エラーにしない。
- 見送り: Foundation Models を Swift から直接呼ぶネイティブ版(Xcode と iOS ビルドが要る。アプリから呼べるのはオンデバイスだけ)、
  Chrome の内蔵 AI(この Mac で確かめられない)、中継で無料枠を配る(運用と費用が作者に乗る)。

### これからの候補(未決。上から順に検討)
1. **コース型レコメンド**: 無限のキューではなく「このテーマの入門 10 本」。サーベイ → 古典 → 最近の順。終わりと進捗が見える。
2. ~~LLM の費用を誰が持つか~~ → Q27 で決定。
3. ~~要約の根拠を見せる~~(2026-09-18 実装。spec 7.2。ページ番号は見送り): 各主張に本文の引用とページ。アブストだけのときはその旨のバッジ。
4. ~~採点を差分フィードバックに~~(2026-09-18 実装。spec 7.2): 点数より「見落とした点」「誤読かもしれない点」。Lv1 のメモに 20 点満点の採点は酷。
5. **記事への対応**: URL を取り込み、Zenn・技術ブログ・解説記事も 1 本として扱う。論文が重い日の逃げ道。
6. **スマホの入口**: PWA、共有シートから「あとで読む」、今日の 1 本を 3 枚のカードから選ぶ。
7. **記録を資産にする**: 1 週間後の再提示、月次で関連研究の下書き、ヒートマップ。
8. **削る・隠す**: BibTeX、検索ソース選択、Ollama、ポモドーロ、使用量表示を詳細設定の奥へ。
9. **厳しさ**: 罰はアプリごとやめる原因になる。ストリークフリーズと「2 日連続では休まない」程度に。
